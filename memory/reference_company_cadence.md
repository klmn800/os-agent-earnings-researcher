The data layer for [[window-gating-and-noop-sessions]]: `window_opens = earnings_date − lead_time − buffer`, where **lead_time** is a company's historical gap between its advance "to Announce" / "Sets the Date" PR and the actual release. Before the window opens, the PR *cannot exist yet* — skip with a logged next-check date instead of researching.

Seeded 2026-05-28 from `research_log.md` + `archive/research_log_2026-Q2_spring-earnings.md`; grows each maintenance session. Lead times are approximate. `—` = not yet observed. Times: bmo = before market open, amc = after market close.

## Two standing rules (learned the expensive way)

**1. "Issues no advance PR" ≠ "no company source." Check the events calendar before giving up.**
The PR feed and the IR **events calendar** are *different surfaces*. A company can publish
zero scheduling PRs and still pre-list its earnings date — sometimes months out. This cost
three sessions on **SQM** (written off as unresearchable, escalated to Ben; the calendar had
both the release *and* call datetimes all along) and repeated deferrals on **DELL**. Symbols
where the calendar is the primary source: **SQM, DELL, DNN, MCHP, LOW, HD**. Try
`/news-events/events-calendar`, `/events-and-presentations`, `/news-events/upcoming-events`,
`/events` — one batched fetch, four guesses. ⚠ It does *not* generalise universally (08-13:
COTY/NIO/PDD/PVH/NCNO 404 on all four; GTLB/WSM return JS-only shells) — so it's one cheap
attempt per gated symbol, not a hunt.

**2. Try `urllib` + browser UA BEFORE concluding a host is unreachable.**
"WebFetch times out" and "the host is down" are different facts, and conflating them has
put wrong entries in this table. Confirmed WebFetch-fails-but-urllib+UA-works:
**DELL, SQM, NCNO, PVH, AMGN, AME, BWXT, FANG, LI**. Also keep **four** failure modes distinct
when writing notes here — **NXDOMAIN** (no host, stop), **404** (wrong path, try another),
**200-but-JS-only** (right path, no data server-side, stop trying paths), and
**200-for-everything** (bot wall — see rule 3). Prior notes
collapsed these and produced false "no source exists" conclusions.

**3. Before trusting an existence probe, probe a nonsense path on the same host first.**
The slug-probe technique (guess a formulaic PR URL; 404 ⇒ not issued, 200 ⇒ issued) is the
cheapest in-window check available — PVH, DTE — but it is only sound on a host that **404s
honestly**. Found 2026-08-17: `www.copart.com/investor-relations/` returns **200**, and so
does `www.copart.com/this-path-does-not-exist-zzz/` — identical ~1KB `NOINDEX,NOFOLLOW`
interstitial. On a host like that every guess reads as "the PR exists," so the probe does not
merely fail, **it fails in the confirming direction**. One extra request for a deliberately
nonsense path converts the method from "usually right" to "verified sound here." Same family
as CAH's live-but-dead feed (HTTP 200, one item from Nov 2024): a response that passes a
naive check while carrying no information.

- **⚠⚠ A weekday habit is quarter-scoped too — and so is every cadence claim you quote. (2026-08-28, ORCL.)** Companion to the `+364d` rule above, from the same failure shape one quarter over. Three sessions justified Oracle's stored **09-10** with *"the 10th, three quarters running"* — true, but those three were **Q2, Q3 and Q4**. Oracle's **Q1** has a different habit entirely: **Mon or Tue, 5/5 since 2021**, in a Sep 9–17 band. The stored date is a **Thursday**. Nothing contradicts it (2020, the exact Labor-Day calendar analog, was a Thursday), but the argument that made it sound settled was borrowed from quarters it does not describe, and `+364d` actually points one slot earlier. **Practice: before quoting a date pattern OR a weekday pattern as support, filter the furnish history to the SAME fiscal quarter and say how many observations survive that filter.** Ran across four symbols in one EDGAR sweep the same session, it cleanly separated them: ADBE Q3 (Thu 4/4, one day earlier each year) and GME Q2 (Tue/Wed 7/7, five-day band) are tight enough that the corroborator means something; ORCL Q1 and CPRT Q4 are not.
- **⚠ A multi-year band can be two REGIMES, not one distribution — check for a step change before quoting its width. (2026-08-28, CPRT.)** This table quoted Copart Q4 as a "Sep 3 → Sep 20 band," implying ~3 weeks of noise. The 18-year history shows something else: **2008–2018 drifted monotonically from Sep 25 to Sep 19, then 2019 stepped down to Sep 5 and stayed there** (Sep 3–14 since). It is not one wide band, it is a **narrow band plus a decade of obsolete history**, and the obsolete half was inflating the apparent uncertainty. Within the live regime the weekday rule is also clean (**Wed or Thu, 7/7**), which is what let an overdue-PR floor of ≥ 09-04 narrow the candidates to just **09-09 / 09-10**. **Practice: plot the full history before quoting a band — a monotone drift ending in a step is a regime change, and only the post-step era is evidence.**
- **✅ A third-party date can be disqualified outright by the market calendar — check holidays before weighing a dissent. (2026-08-28, ORCL/GME.)** finnhub put both Oracle and GameStop on **2026-09-07**, which is **Labor Day** — markets closed, an impossible earnings date, so it needs no research at all to discard. Worth noting *why* it is wrong, because the mechanism will recur: Oracle's Q1 habit really is Monday, so 09-07 is exactly what a weekday-pattern generator produces **when it has no holiday calendar**. That makes an impossible-date dissent a signal about the *source*, not just that one row — expect the same generator to be wrong on other early-September Mondays. **Practice: run any disputed date against the market calendar first; it is the cheapest disqualifier available and it costs zero web calls.**
- **⚠ An aggregator's "Confirmed" flag is not evidence — and is checkable against structure. (2026-08-26, CPRT.)** investing.com/tipranks both reported Copart Q4 as "Sep 09, **Before Open (Confirmed)**." The date is arguable, but the *timing* is provably false: Copart has furnished Item 2.02 **after the close in 8 of 8 quarters, 16:14–16:27 ET**. A source that is demonstrably wrong on the half you can verify earns no credit on the half you can't. **When a third party volunteers a "confirmed" label, test it against the one field you already have structurally locked (usually bmo/amc from furnish times); if it fails there, discard the whole row.**
- **⚠⚠ A lead time measured from ONE quarter is not a lead time — gate off the LONGEST observed lead. (2026-08-21, WSM.)** The table carried WSM at "~2d, the shortest lead here," from a single Q1 observation (05-19 → 05-21). Its Q2 advance PR actually ran a **7-day** lead (**08-19 09:00 ET → 08-26**), so the `date − 2d` gate said "next check 08-24" and the 08-20 session skipped WSM *by design* while the PR had already been live ~19 hours. Nothing was lost (the release is 08-26 and 08-24 would still have caught it), but the gate was wrong for 2 days and only a batched read found it. **This is the TECH failure shape in miniature — an absence measured against a lead nobody had verified across quarters.** Before trusting any gate, check how many quarters its lead rests on: 1 observation ⇒ treat the gate as advisory and read the feed anyway (it is one curl); 3+ consistent observations ⇒ the gate is sound. Same audit cleared ORCL (3 obs) and CPRT (4 obs) the same session.
- **⚠⚠ Advance PRs mostly publish AFTER the session starts — so `next_check` = `PR_due_date + 1`, not the PR due date.** Observed publication minutes: **GWRE 16:15 ET (3/3)**, **ORCL ~16:01 ET**, **WSM 09:00 ET**, **GTLB 16:05 ET**, **CPRT after 16:00 ET**, **PVH Mon 09:00 ET (3/3)**. Sessions start ~07:1x–07:2x, so a morning read can only ever see PRs published on *previous* days. GWRE is the clean demonstration: the PR landed **08-20 16:15**, the 08-19 and 08-20 morning sessions correctly saw an empty feed, and 08-21 caught it — those two "misses" were structural, not errors. Practical effect: when a symbol's PR is due on day D, schedule the check for **D+1** and do not treat a same-day morning absence as information. For a date that cannot wait, poll the known minute to a **file** (the PVH/BR technique). See [[window-gating-and-noop-sessions]].
- **Feeds converge on the company date ~1 week after the advance PR.** Observed 2026-06-05: CNM (06-10), ADBE (06-11), ORCL (06-10), JBL (06-17) all reached `conflict=0` in `earnings_date_sources` — these are dates I'd confirmed from company PRs back on **05-29**. Two consequences for window-gating: (1) a feed `conflict=0` ~1wk out is *corroboration* of an already-confirmed date, not new information; (2) the wasted-cycle zone is researching *before* the advance PR exists AND before the feeds settle — that early window is where the 0-confirm churn happens. Gate to `earnings_date − lead_time − buffer` and let the feeds + PR mature.
- **⚠⚠ A search-index absence is not an absence — BusinessWire's exact-title search lags ~1 day. (2026-09-01, ADBE/CPRT.)** Adobe's advance PR published **08-31**; the **domain-restricted businesswire.com search returned only prior quarters**, while the open web search and **stocktitan** both carried it. A session running only the documented BW exact-title channel would have logged *"advance not out"* **on the day it published** — and because absence arguments set the **floor** under a date, that false negative silently pushes an earnings date later. This is the same class as the 200-for-everything bot wall: a channel that answers confidently but is wrong in exactly one direction. **Practice: the BW title search is a valid POSITIVE channel, but never trust it as a NEGATIVE on its most recent ~1 day. Any absence that drives a floor must be corroborated on a second, faster-indexing channel** — `stocktitan.net/news/<SYM>/` proved current the same day (it had the 08-31 ADBE release) and is the cheapest cross-check available. Verify the cross-check is itself current by confirming it carries a known-recent PR.
- **⭐⭐ Read PR BODIES, not headlines — a mid-transaction company can move its earnings date into a PR with the wrong title. (2026-09-01, GME.)** GameStop issued no *"Announces Release Date"* advance this quarter. The date was the last bullet of **"GameStop Announces Second Quarter 2026 Preliminary Results"**, a release that existed only *"in connection with the amendments to its convertible notes exchange announced separately today"* — i.e. a securities-disclosure obligation, not an earnings-cadence event. Title-pattern matching (the documented channel for CPRT and ADBE) returns **nothing** for it. **Practice: when the feed is already being fetched, parse `<description>` bodies and grep for the date language (`expects to release`, `will release`, `will report`) rather than matching the advance-PR title. It costs nothing on a feed you are pulling anyway.** Highest-risk symbols are those mid-transaction (notes exchange, M&A, offering) — exactly when a preliminary-results PR becomes likely. Corollary: for such symbols, *advance-PR absence* has a **third** interpretation beyond issued/skipped — **the information relocated**.
